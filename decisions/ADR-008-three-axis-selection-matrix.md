# ADR-008: Prompt 调优三维选型矩阵 — 精度 × 速度 × 成本

**状态**：已实施
**日期**：2026-05-31
**决策者**：项目组

## 背景

方向 3 跑了三组 Prompt 调优实验：**#4 零样本 / #2 +few-shot / #3 +few-shot+CoT**。原本只有精度+速度两轴对比，结论倾向"生产推荐 #2 综合最稳"。

项目负责人提醒：**"精度、速度、成本怎么取舍"**——成本维度缺失。补齐第三轴后，原结论需要修订。

## 决策

### 1. 在抽取层透传 token usage

修改 `textTagExtractor.ts` 的 `callTagLlm`，捕获 OpenAI 兼容协议返回的 `usage` 字段（`prompt_tokens` / `completion_tokens` / `total_tokens`），透传到 `Q22TagResult` / `TextTagResult` 的可选 `usage` 字段。

修改 `scripts/run-eval.ts`，在 `EvalRecord` 中存 token 三元组，按字段和整体汇总输出。

### 2. 三维对比数据（244 条评测集，gpt-4.1）

| 方法 | 精度 | 速度 | tok/样本 | prompt | completion | 100 万次成本（$2/M prompt + $8/M completion） |
|---|---|---|---|---|---|---|
| **#4 零样本** | **97.5%** | **1464ms** | **732** | 678 | 54 | **$1788** |
| **#2 +few-shot** | 96.7% | 1603ms | 1036 (+41%) | 963 | 74 | $2518 |
| **#3 +few-shot+CoT** | **97.5%** | 1573ms | **1154 (+58%)** | 1084 | 70 | **$2738** |

### 3. 关键洞察

- **零样本不是最贵的——它最便宜**。仅 732 tok/样本，精度和 #3 并列最高
- **few-shot 成本主要堆在 prompt 部分**（+304 prompt tok 来自硬塞 4 条示例），不是 completion。每次调用都付一遍这个固定开销
- **CoT 在 #2 之上再 +118 prompt tok 换 1 条 longtail 修对**（探店、中央空调裸词），全字段开 CoT 的性价比低
- **整体准确率不区分 #4/#3**（都是 97.5%），但子维度取舍很不同：CoT 修对 Q22 longtail 但 Q22 互动维度准确率波动 -8.7pp、子标签命中率 -8.9pp（注意力分散）

### 4. 修订后的工程选型矩阵

| 场景 | 推荐方法 | 理由 |
|---|---|---|
| 极致省钱（成本敏感、批量离线打标） | **#4 零样本** | 精度天花板已 97.5%，子标签命中率 55% 较低但主标签可用 |
| 生产平衡（默认推荐） | **#2 +few-shot** | sub 字段命中率从 70%→90% 大幅可用，主标签持平，+41% 成本换 +20pp 子标签可用度 |
| 已知 longtail 高发字段 | **按字段开 CoT** | 仅 Q22 加 CoT（网络词密集），Q23/Q24 不加。避免全字段都开造成 +13% 成本只换 1 条 longtail 修对 |
| 高预算 + 强解释性需求（PPT demo、可解释性研究） | **#3 +CoT** | reasoning 字段本身有展示价值 |

### 5. 月成本估算（按 1 QPS、3 字段并行）

每天约 26 万次抽取调用：
- **#4**：月度 $14k
- **#2**：月度 $20k（+$6k 换 sub 字段从 70%→90% 可用，**值得**）
- **#3**：月度 $22k（再 +$2k 换 1 条 longtail 修对，**全字段开不划算**）

## 为什么不选其他方案

- **保留原结论"生产推荐 #2"不修订**：忽略了零样本的成本优势，且没有按场景细分
- **不加 token 计量**：缺少第三轴数据，方向 3 的"取舍"问题无法回答
- **按 prompt 字符数估算 token**：误差 10-20%，月度成本估算会失真
- **全字段都开 CoT**：边际收益递减（Q23/Q24 longtail 没改善），且互动维度副作用明显

## 实现文件

| 文件 | 改动 |
|---|---|
| `src/textTagExtractor.ts` | `callTagLlm` 返回 `{ content, usage }`；两个 extract 函数透传 usage |
| `src/tagTree.ts` | 新增 `TokenUsage` 接口；结果对象加可选 `usage` 字段 |
| `scripts/run-eval.ts` | `EvalRecord` 存 token；`summarize()` 聚合每字段+整体；Markdown 报告输出 token 用量章节 |
| `eval/BASELINE.md` | 新增"三维对比"章节 + 修订后的工程选型矩阵 |

## 后果

- **方向 3 的"取舍"问题被完整回答**：精度、速度、成本三轴都有真实数字支撑
- **PPT 选型建议从单一推荐变为场景化矩阵**：更接近真实工程决策
- **PPT 叙事亮点**：原本以为加 few-shot 和 CoT 一定更好，加上成本维度后**零样本反而是最划算的"够用"方案**——这是反直觉的实证发现，比"#2 最稳"更有说服力
- **未来引入新方法（new model、self-consistency 等）**：评测脚本已具备 token 计量能力，三维对比可零成本复用
