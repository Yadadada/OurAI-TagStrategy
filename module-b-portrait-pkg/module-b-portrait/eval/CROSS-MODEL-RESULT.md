## gemini fallback 7.0% 的根因分析

第一次跑 gemini 时 fallback 占比为 32.8%（精度 75.0%），重跑后降到 7.0%（精度 95.3%）。差异来源于 **proxy 端偶发故障，不是模型/数据/prompt 问题**。

### 故障分类（基于 stderr 日志）

| 失败类型 | 条数 | HTTP | 表现 |
|---|---|---|---|
| Proxy 502 Bad Gateway | 8 | 502 | 立即返回，耗时 ~12s（proxy 内部重试后吐 502） |
| Timeout abort（30s） | 6 | — | 上游卡死直到客户端 30s 超时 |
| LLM 返回但没合法主标签 | ~4 | 200 | LLM 输出 JSON 但 main 不在白名单，被 parseTagJson 当空数组 |
| **合计 fallback** | **18 / 256 = 7.0%** | | |

### 关键证据：第一次跑的 84 条 fallback 是同一类故障的"放大版"

- 上次 84 条 fallback 中 **100% totalTokens=0** + 全部耗时 ~12.4s 高度一致
- 这次 q23-011 ~ q23-exp-003 出现 7 条连续 12s 一致失败的"proxy 抖动指纹"，与上次完全同形态
- 推断：上次评测时 proxy 处于异常状态，对 gemini 上游的某个时间窗口大批量 502，造成假性 75% 准确率

### 工程改进建议（写进 PPT 的"工程优化"章节）

1. 对 5xx 加 1-2 次指数退避重试（OpenAI/Anthropic/Gemini 三路统一）
2. 把客户端 30s timeout 调到 45s，容忍 gemini-2.5-pro 这类 thinking 模型的尾延迟
3. 在评测脚本里把"健康检查"扩展为"分批健康检查"——每跑 50 条样本探测一次，连续 ≥ 3 条 fallback 立即 abort，避免 proxy 抖动期跑出无效结果
